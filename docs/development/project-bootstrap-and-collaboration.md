## 1. 分支与需求基线

框架分支直接从 `main` 创建，与 `docs/requirements-srs-draft` 的需求材料 PR 分别推进。框架分支不合入该需求分支，也不复制其中的 SRS、独立用户故事清单或模型文件。

当前可引用的需求基线是主分支中的阶段调研报告。需求 PR 合入 `main` 后，将 `main` 的更新合入框架工作分支，并将需求引用衔接到独立用户故事清单和 SRS，沿用原 US 编号。技术实现不得自行改变故事验收标准；需求变化通过 Issue 提出并在 PR 中记录评审结果。

框架准备是编码前的工程任务。课程规定的需求、分析与设计规约及其评审仍按教学进度完成；本文件不代替完整设计规约和正式评审记录。

## 2. 技术栈与架构选择

项目采用单仓库、前后端分目录、后端按业务模块组织的单体架构。一个 Spring Boot 应用提供业务服务，一个 MySQL 数据库存储业务数据。该结构便于四人小组统一启动、联调、测试和部署，同时保持业务模块边界。

| 部分 | 采用方案 | 用途与约定 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite | 页面组件化开发、类型检查和构建 |
| 前端配套 | Vue Router、Pinia、Element Plus | 页面路由、共享状态和常用界面组件 |
| 后端 | Java 21 LTS、Spring Boot | 提供 HTTP 接口、业务处理和实时消息服务 |
| 后端构建 | Maven Wrapper | 仓库提供统一 Maven 版本，包含 Unix 和 Windows 启动脚本 |
| 登录与会话 | Spring Security、Spring Session JDBC | 服务端统一认证授权，本站会话持久化到数据库 |
| 数据访问 | MyBatis、MySQL 8.4、Flyway | 显式 SQL、事务处理与数据库结构版本管理 |
| 实时消息 | REST API、WebSocket | HTTP 处理业务请求和历史读取，WebSocket 推送在线消息 |
| 接口契约 | OpenAPI | 统一描述请求、响应、错误与鉴权要求 |
| 测试 | Spring Boot Test、JUnit、Vitest、Playwright | 后端业务测试、前端测试及关键用户流程验收 |
| 环境与部署 | Docker Compose、Nginx | 统一本地依赖环境，部署时提供静态页面和反向代理 |
| 工程流水线 | GitHub Actions | 自动检查、构建、测试和后续部署 |

前端使用 pnpm 管理依赖并提交锁文件；Node.js 选择受支持的 LTS 版本。初始化时选择与 Java 21 及相关库兼容、仍受支持的 Spring Boot 稳定版本，将具体版本固定在构建文件和环境说明中。依赖升级通过独立任务和 PR 验证，不在共享配置中使用浮动版本。

初始架构不引入微服务、Redis、消息队列和独立搜索集群。会话使用数据库存储，帖子搜索先由 MySQL 实现；后续确有性能或功能依据时，通过设计变更评审引入新组件。

## 4. 接口、权限与数据库约定

### 4.1 接口契约

`contracts/` 中的 OpenAPI 文件作为 HTTP 接口契约来源。开发前约定接口路径、请求参数、响应结构、错误码、分页和访问条件，前后端据此并行实现。契约与接口实现变更放入同一 PR，不同时维护两套独立的接口说明。

接口统一使用 `/api/v1` 前缀和明确的 HTTP 状态码。时间以统一时间基准存储，接口使用带时区的 ISO 8601 表达，页面按北京时间展示。分页、错误响应和公共字段的具体结构在框架接口契约中统一定义。

WebSocket 的事件类型、载荷、确认及重连行为另行记录在 `contracts/`，与私聊 HTTP 接口共同引用故事验收标准。消息推送不替代持久化；服务端保存成功后才确认发送成功，离线或重连通过历史接口补齐消息。

### 4.2 登录与权限

QQ／微信有效登录后创建或定位本站普通账号，不设置游客账号或独立密码注册。以服务端核验后的渠道、应用标识和渠道用户标识定位账号，不按昵称或头像自动合并账号。

本站采用服务端会话与 HttpOnly Cookie；部署使用 HTTPS 和 Secure Cookie，结合登录回调方式配置 SameSite。写操作启用适合会话认证的 CSRF 防护；前端开发代理与部署反向代理统一应用访问入口。

服务端校验账号状态、资源所有权、会话参与关系与管理范围。WebSocket 连接、消息投递和会话失效处理同样执行权限控制，不能仅依赖页面隐藏按钮。

普通交流资格、VIP 有效期和管理授权分别维护。版主或管理员可以同时拥有 VIP，会员到期不取消管理授权；客户端提交的角色或会员字段不能作为授权依据。

### 4.3 数据库与配置

所有共享数据库结构变更通过 Flyway 迁移脚本进入 Git。已在共享环境执行的迁移脚本保持不变，后续调整新增迁移；合并前检查迁移版本冲突。

开发数据可重复初始化，并与部署环境区分。登录映射、消息请求标识、支付订单等关键唯一性由数据库约束与业务事务共同保障。订单套餐保存购买时的快照，同一订单仅发放一次会员权益。

仓库提供 `.env.example` 和配置说明。真实密钥、证书和本地环境文件不提交；部署凭据由运行环境或 GitHub Secrets 提供。

## 5. 外部服务与本地联调

QQ 登录、微信登录、支付宝和微信支付分别封装适配器。微信登录与微信支付使用各自的接入配置，登录成功不授予会员权益。

框架阶段建立外部接入核验任务，确认各渠道的应用或商户条件、审核要求、回调地址及实际可用的测试能力，尽早验证关键调用链。

本地开发和自动化测试可在 `dev`／`test` 环境使用适配器模拟实现，模拟身份也遵守普通账号和权限规则。部署配置禁用模拟登录与模拟支付；测试替身不能作为真实外部集成已完成的验收证据。接入条件影响需求实现时，通过需求变更 Issue 评审处理。

## 6. 用户故事 Issue 与完成标准

28 条用户故事分别建立 Issue，标题保留 US 编号，每条指定一名主要负责人。负责人负责推动需求澄清、实现、测试和验收，可以与其他成员共同开发。人员分配和调整以 Issue 的 Assignee 及讨论记录为准。

故事 Issue 包含：US 编号、故事描述、Given／When／Then、文档引用、主要负责人、Milestone、依赖任务和验收证据。安全与性能故事同样建立 Issue，由负责人统筹跨模块验证。

工作量较大的故事可以拆成前端、后端、测试等关联任务。框架、CI、数据库初始化、缺陷修复等工程活动单独建立 Issue，并关联其支持的故事或增量，不另造用户需求编号。

故事执行流程：

1. 明确验收标准、依赖和接口契约，认领 Issue。
2. 创建短期任务分支，提交实现、相关测试和必要文档。
3. 创建 PR，关联 Issue，说明行为变化、验证结果及 AI 使用情况。
4. 完成 CI 检查、人工评审和故事验收，处理评审意见。
5. 合并后关闭已完整交付的故事，更新 Projects 和 Milestone。

只完成部分工作时，PR 使用 `Refs #编号`；完整实现且满足验收条件时使用 `Closes #编号`。关联子任务完成不等于父故事完成。

故事关闭必须同时满足：所需页面和接口可联调、验收场景通过、权限和异常路径经过验证、相关测试及文档更新、PR 评审与必要 CI 检查通过。安全和性能故事以其测试报告及验收指标为依据关闭。

## 7. 四人协作与评审安排

张启政作为组长统筹工程基础、接口约定、集成和最终合并，并参与账号权限实现。其余成员按 Issue 认领业务任务；下表用于划分协作范围，不替代具体任务的人员分配。

| 工作范围 | 主要交付 | 协作接口 |
| --- | --- | --- |
| 工程基础与账号权限 | 框架、CI、QQ／微信登录、会话、公共约定 | 向各模块提供当前用户与权限校验能力 |
| 论坛与公开内容治理 | 板块、帖子、评论、搜索、公开内容举报处理 | 协作处理用户资料、管理授权和会员展示 |
| 私聊 | 会话、消息、未读、拉黑、可靠性与性能验证 | 对接用户查询、账号状态和私聊举报证据 |
| VIP 与支付 | 套餐、订单、支付、有效期、金色昵称与主页装扮 | 提供权益查询，协作完成套餐和订单管理 |

每名成员尽量交付能演示的业务功能，并参与对应接口、页面和测试；熟悉前端或测试的成员可以跨模块协助。跨模块的管理员与举报功能在拆分 Issue 时明确主要负责人和协作者，避免职责遗漏。

项目管理、需求分析、架构设计、开发、测试质量和 AI 使用管理等课程职责由四名成员兼任，具体职责随任务记录。两轮迭代之间至少交换一次结对或评审对象。

每个 PR 至少由一名非作者成员评审。组长保留最终合并职责；组长自己的 PR 由其他成员评审。分支保护和 CODEOWNERS 配置须支持该安排，避免作者成为自己 PR 唯一有效的审批人，不以 bypass 替代正常评审。

## 8. Git、CI 与发布约定

`main` 保持可集成状态，禁止直接推送，通过 PR 合并。使用 `feat/`、`fix/`、`chore/`、`docs/` 等短期任务分支，合并后删除；不为每名成员维护长期独立开发分支。

框架文档与后续骨架工作集中在 `chore/project-bootstrap`。各独立功能任务从最新 `main` 建分支；存在依赖时记录在 Issue 中并安排集成顺序。共享框架、接口或数据库变更应及时评审合入，减少长期分叉。

| 流水线环节 | 检查或动作 |
| --- | --- |
| `push`、`pull_request` | 前端类型与格式检查、测试、构建；后端编译、测试与构建 |
| 数据库相关验证 | 在隔离测试数据库执行迁移和必要集成测试，验证真实约束及事务行为 |
| PR 合并门禁 | 必需 CI 检查成功，非作者评审通过，评审意见已处理 |
| 部署与发布 | 在部署环境配置完成后，由 Actions 执行部署；每个增量发布 Tag 和 Release |

前后端公共代码、契约和数据库变化纳入对应检查范围。检查不能通过跳过测试、占位成功脚本或忽略失败结果制造绿灯。核心模块声明覆盖率范围和结果，验收测试依据用户故事编写。

开发期 Compose 优先提供 MySQL 等依赖，前后端可在宿主机运行以便调试。部署使用 Nginx 提供前端静态页面，代理 API 与 WebSocket 到 Spring Boot，业务服务连接 MySQL。

## 9. 框架搭建顺序与验收

框架建设作为工程 Issue 推进，依次完成：

1. 初始化前后端工程，固定运行环境与构建工具版本。
2. 提供 Compose、配置示例、数据库迁移和开发数据初始化方式。
3. 建立公共接口约定、错误处理、会话安全配置与业务模块边界。
4. 完成浏览器经后端访问开发数据库的最小联通流程及相关验证。
5. 接通前后端 CI，提供 Issue／PR 模板和 README 开发指引。
6. 由组员按文档复现启动流程，经评审后合并框架 PR。

框架 PR 的验收条件：

- 四名成员可以按仓库文档完成依赖准备、配置和启动。
- 浏览器可以通过后端读取开发数据库中的约定示例数据，联通验证符合会话和访问控制约定。
- 空数据库可以通过迁移与开发初始化复现所需结构及数据。
- 前后端构建和基础测试可在本地与 CI 执行，失败时阻止合并。
- README 说明启动、测试、配置和常见环境问题，接口契约与贡献流程可供成员使用。
- PR 关联框架 Issue，包含验证结果与人工评审记录。
